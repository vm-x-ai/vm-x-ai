# Contributing to VM-X AI

Thanks for your interest in contributing! This page is the entry point. The
deep dives live under [`contributing-docs/`](./contributing-docs/) — keep this
file short and link out.

## Project structure

VM-X AI is an Nx + pnpm monorepo:

- **`packages/api`** — NestJS gateway. Exposes three completion surfaces
  (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages) and routes
  to provider plugins. Owns auth, audit, cost, migrations and codegen.
- **`packages/ui`** — Next.js dashboard. Talks to the API through a fully
  typed SDK generated by `@hey-api/openapi-ts`.
- **`packages/libs/shared`** — TypeScript types and helpers shared between
  api and ui.
- **`docs`** — Docusaurus user-facing site (separate from `contributing-docs/`).

## Wire-format invariant

The gateway preserves each upstream provider's wire format **verbatim**. The
public surface a client picked (OpenAI Chat Completions, OpenAI Responses or
Anthropic Messages) determines the response shape — converters in the
provider plugin layer normalize across providers when the surface and
upstream don't match. Do not normalize provider quirks anywhere else in the
request/response path. See
[`contributing-docs/ai-providers.md`](./contributing-docs/ai-providers.md)
and [`contributing-docs/conversion-matrix.md`](./contributing-docs/conversion-matrix.md).

## Quick start

Full setup details (env files, ports, OIDC) are in
[`dev-setup.md`](./contributing-docs/dev-setup.md). The short version:

```bash
pnpm install

# Backing services (Postgres :5440, Redis cluster :7001-7003)
docker compose up -d postgres redis redis2 redis3 redis-cluster-init

# Apply migrations + regenerate Kysely types
pnpm exec nx run api:migrate
pnpm exec nx run api:codegen

# Run api + ui (two terminals or via run-many)
pnpm exec nx run api:serve      # http://localhost:3030/api
pnpm exec nx run ui:dev         # http://localhost:3001
```

After API DTO or endpoint changes, regenerate the UI SDK:

```bash
pnpm exec nx run ui:gen-client
```

## Tests

The api test target ships three vitest projects plus combined configs:

```bash
pnpm exec nx run api:test:unit          # default for `api:test` and `nx affected -t test`
pnpm exec nx run api:test:integration   # mocked-DI orchestrator + resource specs
pnpm exec nx run api:test:live          # hits real provider APIs (auto-skips without keys)
pnpm exec nx run api:test:all           # all three, no coverage
pnpm exec nx run api:test:coverage      # all three, merged v8 coverage
```

Live tests read provider keys from `.env.local` at workspace or project root
and gracefully skip when the matching key is missing. See
[`integration-tests.md`](./contributing-docs/integration-tests.md) for the
full env-var table, and [`nx-commands.md`](./contributing-docs/nx-commands.md)
for the rest of the workspace targets.

UI end-to-end specs run against a live api + ui pair:

```bash
pnpm exec nx run ui:e2e
```

## Code style

- TypeScript everywhere. No `any` unless commented and unavoidable.
- Existing code is the source of truth — match neighboring files for naming,
  imports, file layout, and test style.
- Run lint and typecheck before opening a PR:

  ```bash
  pnpm exec nx run api:lint
  pnpm exec nx run api:typecheck
  pnpm exec nx run ui:lint
  # or, across affected projects:
  pnpm exec nx affected -t lint typecheck
  ```

- Husky + lint-staged auto-run `nx format:write` and `nx affected -t lint --fix`
  on commit. Pre-commit messages are checked against
  [Conventional Commits](https://www.conventionalcommits.org/) via commitlint.

## Commit and PR conventions

- **Conventional Commits.** `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`,
  `test:`, `ci:`. Scopes are optional but encouraged for cross-package
  changes (e.g. `feat(api): ...`, `fix(ui): ...`).
- **One logical change per PR.** Keep diffs reviewable.
- **Branch from `main`** (`git checkout -b feat/short-slug`).
- **PR description** should state the user-visible behavior change, link any
  related issues, and call out anything reviewers should verify manually
  (env-var changes, migration ordering, provider key requirements).
- **Generated files commit alongside the source change.** Migrations land
  with their regenerated `entities.generated.ts`; API DTO changes land with
  the regenerated UI SDK under `packages/ui/src/clients/api/`.
- **Do not reference customer or third-party org names in source, specs, or
  contributing docs.** Use neutral wording (e.g. "a downstream client",
  "an upstream provider").

## Common workflows

- **Adding a database migration** —
  [`database.md`](./contributing-docs/database.md). Create the migration file,
  register it in `migrations.service.ts`, run `api:migrate`, then `api:codegen`,
  then commit both the migration and the regenerated entities.
- **Adding or changing an API endpoint** —
  [`openapi-codegen.md`](./contributing-docs/openapi-codegen.md). Annotate
  with `@ApiOperation({ operationId })` and `@ApiOkResponse({ type })`, run
  `ui:gen-client` against a running api, commit the regenerated client.
- **Adding a provider** —
  [`ai-providers.md`](./contributing-docs/ai-providers.md). Create the
  per-provider folder with one file per surface plus `index.ts`. Keep
  upstream wire format intact; put any cross-surface translation in the
  provider's converter, not in the gateway service layer.
